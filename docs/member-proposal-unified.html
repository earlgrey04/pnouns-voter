pNouns ⚡ DAO — 運営からの提案

Snapshot での投票はそのまま。その前後の手作業をなくします

2026年8月21日 ・ アールグレイ ・ 「いまの仕組み」と「新しい仕組み」を並べて、何が変わり、何が変わらないのか、費用と安全性はどうなのかをまとめました。文中の事実はすべて公開データで検証できます(§10)。

3 行まとめ
  • メンバーの投票は今までどおり Snapshot・ガス代 0 円。変わりません。
  • その後の「結果を確認して Nouns DAO に投票する」人手作業(年 20〜28 時間)を、署名をオンチェーンで検証して自動投票する仕組みに置き換えます。費用はガス代のみ 年 約 0.002〜0.004 ETH(500〜1,100 円)。当面は委任アドレスにある既存のガス代から賄うため、新たなトレジャリー支出はありません。
  • テストネットで通し検証済み・第三者(AI)監査 15 回。本番はまず「投票しない見学モード」から始め、いつでも 1 操作で手動運用に戻せます。

1.提案 1 本ごとの流れ

いまの仕組み

  1. 自動ローカル 自宅 PC が Nouns の新提案を検知し、AI で日本語要約を作る
  2. 人クラウド アールグレイが要約を確認・修正して承認
  3. 自動クラウド Snapshot に投票ページを作成(本文＝日本語要約)
  4. 人クラウド Discord に「投票してください」と告知
  5. メンバークラウド Snapshot で投票(署名・ガス代 0 円)
  6. 人オンチェーン 締切を見張り、結果を確認し、自分のウォレットから Nouns DAO に投票
  7. 人クラウド Discord に結果を報告

新しい仕組み

  1. 自動クラウド Nouns の新提案を検知(Cloudflare 上・自宅 PC 不要)
  2. 自動クラウド Snapshot に投票ページを作成(GitHub 上)。本文は Nouns の提案文をそのまま転記(長すぎる場合のみ末尾を省略し、原文リンクを表示)
  3. 自動オンチェーン 「この Snapshot 投票は Nouns の第 N 号議案のもの」という対応付けを記録
  4. 自動クラウド Discord に告知(投票リンク・締切つき)
  5. メンバークラウド Snapshot で投票 (画面も手順も変わりません・ガス代 0 円)
  6. 自動オンチェーン 投票の署名がコントラクトに届き、本物か検証され、NFT の枚数で集計される
  7. 自動オンチェーン 締切後、コントラクトが集計どおり Nouns DAO に投票
  8. 自動クラウド Discord に結果を報告(検証リンクつき)
変わること
  • 人の作業がなくなります(要約の承認・告知・Nouns への投票・結果報告)。集計から投票・報告までの流れは自宅 PC にも依存しません。
  • Snapshot の提案文が「日本語要約」から「Nouns の原文(英語)そのまま」に変わります。画像や見出しもそのまま表示されます。日本語の要約は別途 Discord に投稿する形を予定しています(自動化するかは検討中)。
変わらないこと: メンバーの投票体験。今までどおり Snapshot で、署名だけ・ガス代 0 円で投票します(ETH を持っていないウォレットでも投票できます)。

2.誰が何を持つか — 権限と鍵

いまの仕組み

  • Nouns の投票権 … マルチシグ → アールグレイ個人のウォレットに委任
  • 投票の判断 … 人が Snapshot の結果を読んで手で実行
  • Snapshot の結果と Nouns への投票の一致は、人が正しくやったと信じるしかない
  • アールグレイが不在・多忙だと止まる

新しい仕組み

  • Nouns の投票権 … マルチシグ → コントラクトに委任(個人は持たない)
  • 投票の判断 … コントラクトが署名を検証して自動集計。運営もクラウドも結果を変えられない
  • 集計の内訳が Nouns DAO の記録に残る(§5)。誰でも検算できる
  • クラウドが止まっても投票は無効にならない。誰でも代わりに反映・実行できる(§6)

この仕組みを動かす 4 つの鍵 — 誰が何をでき、何をできないか

自動化にはチェーンや Snapshot へ送信するための鍵(ウォレット)が要ります。大事なのは1 本の万能な鍵を作らないことです。役割ごとに独立した鍵に分け、それぞれに「できること」を最小限だけ持たせます。この分担はテストネット上で実際に構成して動作確認済みです。

いちばん漏れやすい場所(クラウド)に、いちばん弱い権限しか置かないという考え方です。仮にクラウドの鍵が盗まれても、できるのは「運ぶのを止める・遅らせる」ことだけで、票の偽造も勝手な投票もできません。ガス払い戻しの悪用もできません — 払い戻しは「本物の署名を実際に反映できた仕事」にしか出ず(同じ票の再提出は失敗して 1 円も出ません)、使った以上の額は戻らず、提案ごとの累計上限(0.02 ETH)と管理者の無効化スイッチで頭打ちになるためです。そもそも投函は誰でも実行できる操作なので、リレイヤーの鍵が漏れても「払い戻しを受けられる」能力は何も増えません。対処は鍵の差し替えだけで済みます。本番では 4 つの鍵が同一アドレスだとプログラムが起動を拒否する仕掛けも入っています。置き場所を分けているのにも理由があります — 特に Snapshot bot と登録係は同じ場所に置きません。両方が同時に盗まれると「偽の投票ページを作り、それを対応表に登録する」攻撃(§3 の自動検算では見抜けない唯一のケース)が 1 箇所への侵入だけで成立してしまうためで、別の場所に分けておけば攻撃者は 2 つの独立したサービスを同時に破る必要があります。管理者権限の移管(委任アドレス → マルチシグ)は 1 トランザクションで、テストネットで移管の往復を演習済みです。

ガス代(ETH)を持たせるのはリレイヤーと登録係の 2 つだけです。リレイヤーは票の投函のたびにガスを立て替えますが、同じ処理の中でプールから払い戻されるため少額(本番想定 0.01 ETH)が回り続けます。登録係の登録操作には払い戻しがなく自分の残高を消費しますが、1 回あたり約 1 円 × 年 50〜110 回なので 0.005 ETH で数年もちます(払い戻しを付けないのは意図的です — 払い戻し対象を「誰でも実行できる救済操作」に限ることで、万一登録係の鍵が漏れても登録の繰り返しでプールを吸い出す抜け道にならないようにしています)。両方とも自動プログラムが残高を監視し、少なくなると Discord に⚠️警告を出します(プール・登録係含む)。Snapshot bot は署名だけなのでガス不要、管理者もほぼ不要です。

正直な注記(テスト段階の現在地): いまのテストでは、4 つの鍵はアドレス(権限)としては分離済みですが、保管場所はリレイヤーが Cloudflare にある以外、登録係・bot の鍵は開発用にアールグレイの自宅 PC に同居しています。上で述べた「置き場所の分離」は本番移行時に、鍵を新規生成し直して実施します(手順書に組み込み済み)。

3.「集計が正しい」と言える理由

いちばん大事な前提: コントラクトは「集計結果」を受け取りません。受け取るのは1 票ずつの署名データで、正しさを自分で確かめ、集計も自分で行います。「誰かが計算した結果を信じる」場面がそもそも存在しません。

そもそもコントラクトは Snapshot を読めないのに、どう検証するのか(たとえ話つき)

コントラクトは外部のインターネットに一切アクセスできません(あらゆるスマートコントラクト共通の制約)。Snapshot から署名データをダウンロードするのはリレイヤー(クラウドの自動プログラム)で、トランザクションの引数としてコントラクトに「手渡し」します。つまり運び屋です。

「運び屋が渡すデータなど信用できるのか?」 — ここが設計の核心で、信用しなくていいようにできています。メンバーが snapshot.box で「賛成」を押すと、ウォレットが「誰が・どの投票所の・どの提案に・どの選択肢を・いつ」という構造化されたメッセージ全体に電子署名を作ります(チェーンに書き込まないのでガス代 0 円)。この「メッセージ+署名」の組が Snapshot と IPFS に公開保存され、誰でもダウンロードできます。

電子署名には次の性質があります: 署名とメッセージがあれば、「誰が署名したか」を純粋な計算だけで復元できる(誰かに問い合わせる必要がない)。コントラクトは受け取ったデータから、①メッセージのハッシュ値を自分で計算し直し(このとき投票所名は焼き込み済みの pnounsdao.eth を使う)、②署名から署名者のアドレスを数学的に復元し、③申告された投票者と一致するか照合します。Ethereum 本体が全トランザクションの検証に使っているのと同じ仕組みです。

リレイヤーが途中で「賛成」を「反対」に書き換えると、①のハッシュが変わり、②で復元されるアドレスがまったく別の(実在すらしない)アドレスになり、票は拒否されます。改ざんは「バレる」のではなく数学的に成立しないのです。偽の票をゼロから作るには本人の秘密鍵が必要で、それは本人のウォレットの外に出ません。

たとえるなら: Snapshot は「実印を押した投票はがきが貼り出される公開掲示板」、リレイヤーは「はがきを役所に運ぶだけの配達員」、コントラクトは「印影を自前で照合できる役所」です。役所は掲示板にも配達員にも「本物ですか?」と聞く必要がなく、はがきそのものを検査すれば真贋が分かります。配達員にできるのは配達をサボることだけで、それも掲示板が公開なので誰にでも露見します。

なぜ運営にもクラウドにも書き換えられないのか
  • 署名は 1 文字でも変えると別人の署名になります。「賛成」を「反対」に書き換えて送っても、確認 3 で復元されるアドレスが変わり、本人と一致せず弾かれます。
  • 票の重みは水増しできません。署名には「何枚持っているか」は入っていません。運ぶ側が NFT 番号を添えますが、コントラクトが 1 枚ずつ実際の持ち主を照会するため、他人の NFT や架空の保有は通りません。
  • 別の投票所の署名は使えません。対象の Snapshot スペース名がコントラクトに焼き込まれており、ハッシュ計算に使われます。攻撃者が自分で作った投票所の署名を持ち込んでも成立しません。
使っている暗号は堅牢か

この仕組みが使う暗号部品は Keccak-256(ハッシュ)とECDSA/secp256k1(署名)の 2 つだけで、どちらも Ethereum 本体が全取引の検証に使っているものと同一です(自作の暗号は一切ありません)。Keccak-256 は世界公募(SHA-3 コンペ)の優勝作で、15 年以上の解析を経ても実用的な攻撃は 1 件も見つかっていません。

もしこれらが破られる日が来たら、pNouns の投票どころか Ethereum 上の全資産(Nouns の NFT もトレジャリーも)が同時に危険になります。つまりこの仕組みの暗号的な安全性は「Ethereum 自体と同じ水準」で、ここが相対的な弱点になることはありません。ハッシュの取り方も生の連結ではなく EIP-712 という標準規格で、型情報や用途(snapshot)ごと封印するため、別の文脈で作った署名を投票に流用するすり替えも成立しません。(参考: かつて広く使われた MD5 のように、ハッシュ関数が後年破られた例は実在します。Keccak-256 は出力長も設計世代も異なり、現時点でその兆候はありません)

正直な補足: 遠い将来の量子コンピュータはハッシュより署名側への脅威が先に来るとされますが、これは Ethereum 全体の課題で移行方式が研究されており、この仕組み固有のリスクではありません。実務上の最弱点はアルゴリズムではなく鍵の管理と対応表の運用です — だからこそ鍵の分離(§2)や 24 時間猶予(§3)に力を入れています。

運ぶ側(クラウド)にできてしまうことと、その対策

リレイヤー(運び屋)が悪意を持った場合にできることは、具体的には次の 2 つだけです。

  • 都合の悪い票だけ届けない・遅らせる — 例えば「賛成票だけ運ばず、反対票だけ届ける」ように、届ける票を選り好みして集計を歪めようとする。
  • 票の重みを実際より小さく届ける — 票をチェーンに送るとき、リレイヤーは投票者が持つ NFT の番号一覧を添えます(署名には「何枚持っているか」が入っていないため)。ここで 5 枚持っている人の票に 1 枚分しか添えなければ、その人の票の重みが 5 → 1 に減ります。

どちらにも対策があります。

  • 届けない → 署名は Snapshot 上で公開されているので、誰でも同じ署名を拾って代わりに届けられます(リレイヤーに独占権はありません)。
  • 重みを削る → 誰でも同じ署名に残りの NFT 番号を添えて出し直せます。コントラクトはまだ数えていない NFT の分だけを追加で計上します(同じ人を二重に数えることはありません)。
  • それでも漏れたら → 確定の直前に「Snapshot 上の投票者数」と「チェーン上に反映済みの投票者数」を突き合わせ、足りないままなら本番では自動確定しません(警告を出して人の判断を仰ぎます)。運び漏れが最終結果になることを防ぐ最後の砦です。

唯一、暗号で保証できない部分 — 対応表

確認 1 の対応表(この Snapshot 投票 ＝ Nouns の第 N 号議案)だけは、コントラクトが自力で確かめられません。Snapshot の投票署名に Nouns の議案番号が含まれていないためです(Snapshot の仕様)。運用は全自動ですが、「そのプログラムと鍵を信頼している」という意味で、ここだけは性質が異なります。

そのための備えを 4 段用意しています。

  1. 登録から 24 時間は、その議案の票を受け付けない — 間違いに気づいて登録し直せる時間を必ず確保します。
  2. プログラムが自分で対応付けを検算する — Snapshot に作る提案の本文には、元の Nouns 提案ページの URL(nouns.wtf/vote/第N号)が必ず入っています。プログラムは毎分、対応表の「この Snapshot 提案 = 第 N 号」を取り出すたびに、その Snapshot 提案の本文が本当に第 N 号の URL を指しているかを照合します。食い違っていれば Discord に⚠️警告を出し、本番ではその議案の処理(告知・反映・確定)を止めます。
  3. 対応表はオンチェーンに公開され、Discord の告知にも両方の ID が出るので、誰でも見比べられます。
  4. 最終手段として管理者(pNouns マルチシグ)が停止できます。
備え 1(24 時間の受付停止)と備え 2(自動検算)の詳しい理屈と限界

備え 1「24 時間の受付停止」がなぜ備えになるのか: 対応表はSnapshot 経由の票が 1 票でも受け付けられると、もう取り消せない仕様にしてあります(すでに数えた票の行き先が消えてしまうため、あえてそうしています)。裏を返すと「票を受け付けていない時間」＝「間違えても必ずやり直せる時間」です。24 時間の空白を置くことで、誤登録に気づいて登録し直す余地を必ず確保しています。この 24 時間は登録した時点で確定し、あとから管理者が短縮することもできません。なお猶予中にメンバーが投票しても問題ありません — 票は Snapshot に残り、猶予が明けてから自動で反映されます(テスト済み)。

備え 2「自動検算」の限界: Snapshot に作る提案には、元の Nouns 提案ページの URL(nouns.wtf/vote/第N号)が必ず入っています。プログラムは対応表を使うたびに「この Snapshot 提案は本当に第 N 号議案を指しているか」を自動で照合し、食い違っていれば Discord に⚠️警告を出し、本番ではその議案の処理を停止します。ただし万能ではありません。URL は提案を作った人の自己申告なので、捕まえられるのは「別の提案を取り違えて登録した」類の事故までで、偽の提案と対応表を同じ相手が同時に用意できる場合(登録係の鍵と作成プログラムが同時に乗っ取られた場合)は見抜けません。そこは備え 1・3・4 で受け止める設計です。

4.補えること・補えないこと

Snapshot には「署名だけ・ガス代 0 円」という大きな長所がある一方、結果がブロックチェーンの外にあることから来る弱点もあります。新しい仕組みは長所を残したまま弱点を補うことを狙っていますが、すべては補えません。分けて書きます。

5.オンチェーンに残る記録 — Nouns DAO と pNouns Voter

記録は 2 箇所に残ります。Nouns DAO 側には投票そのもの(理由文に集計の内訳を自動で書き込みます)、pNouns Voter(このコントラクト)側には最終集計と 1 票ごとの明細です。テストネットでの実際の記録:

記録先内容
Nouns DAO(VoteCast)投票者 = pNouns Voter コントラクト ／ 議案番号 ／ 賛否 ／ 票数 ／ 理由文「pNouns holders voted on Snapshot …: FOR (tokens for/against/abstain = 3/0/3, voters = 2/0/1)」
理由文は nouns.wtf の提案ページにコメントとして表示されるため、Nouns コミュニティ全体から「pNouns がどういう内訳でその判断をしたか」が見えます
pNouns Voter(Executed)最終集計(賛成/反対/棄権の枚数と投票者数)
pNouns Voter(1 票ごと)誰が・どの選択肢に・何枚で・いつの署名で投票したか

Snapshot の署名は誰でも取得できるので、第三者が自分で集計し直して上の記録と突き合わせる検証も可能です(§10 に手順)。

6.クラウド(Cloudflare)が止まったらどうなるか

票そのものは Snapshot に残っているので消えません。締切まで 24 時間の余裕を持たせているので、ほとんどの障害は自動で吸収されます。

状況どうなるか必要な操作

Cloudflare の中身は検証できるのか(正直な答え)

直接は検証できません。Cloudflare 上で実際に動いているプログラムが、公開しているソースコードと同一であることを第三者が証明する方法はありません(これは世の中のあらゆるサーバーに共通の限界です)。だからこそ、この設計はクラウドを信頼しないことを前提にしています: クラウドにできるのは署名を「運ぶ」ことだけで、票の中身はすべてオンチェーンのコントラクト(こちらはソースコードとの一致を誰でも検証可能)が確かめます。クラウドの動きも外から観測はできます — 送信したトランザクションは全部チェーン上に残り、設定は公開 API(§10)で見えます。「中身は見えないが、悪さをしても票には触れず、サボれば公開データから分かる」という位置づけです。

9.投票のルール / 導入の進め方

投票のルール(コントラクトに固定)

  • 重み = 保有 pNouns 枚数(チェーン上で検証)。トレジャリー分(13 枚)は数えない。定足数なし。
  • 同数なら投票者数が多い方、それも同数なら棄権 (暫定 — ご意見で変更可能)。誰も投票しなければ Nouns にも投票しない。
  • Snapshot で投票をやり直した場合は、いちばん新しい投票が有効。
  • 締切は Nouns の投票終了の 24 時間前(いまの Snapshot 48 時間より長く投票できます)。
  • コントラクトは後から書き換え不可。NFT や資産は預けません(預けるのはガス代のみ)。

導入の進め方(段階ごとに機械チェックを通します)

  1. 見学モードで設置 — Nouns には投票せず、集計だけを実際の提案で数回行い、手動運用の結果と一致するか確認します。ガス代 0.05 ETH の預け入れ(委任アドレスから)はこの段階で行います(集計の送信にガスが要るため)。この時点のコントラクト管理者はアールグレイの委任アドレスです。
  2. 一致を確認 → メンバーの合意。
  3. マルチシグが投票権の委任先をコントラクトへ変更(1 トランザクション・いつでも戻せる)→ 本番開始。
  4. 安定稼働を確認後、コントラクトの管理者権限を委任アドレスから pNouns マルチシグへ移管(1 トランザクション。移管手順はテストネットで演習済み)。以後、緊急停止・ガス回収・鍵交代はマルチシグの承認が必要になります。

各段階の後に、設定・鍵の分離・委任・残高を機械的に照合するチェックを実行し、全項目が通るまで次へ進みません(手順書と照合プログラムは作成済み・テストネットで検証済み)。

やめたくなったら、マルチシグが委任を戻すだけで元の手動運用に戻せます(Nouns の仕様上、切り戻しは以後の提案から有効。進行中の提案は管理者が停止スイッチで止められます)。
本番移行時に必要な準備
  • Discord の通知先の切り替え: 現在テストの通知はアールグレイのサーバー宛てです。本番では pNouns⚡DAO サーバーの Webhook を発行し、告知(📢)・反映(🗳️)・投票完了(✅)・障害警告(⚠️)を pNouns のチャンネルに流します。投稿先チャンネルとロールメンションの有無は事前に相談させてください。
  • 4 つの鍵の準備: 管理者(当初はアールグレイの委任アドレス → 安定稼働後にマルチシグへ移管)・登録係・リレイヤー・Snapshot bot を別々に用意(テストネットでは構成済み)。
  • ガス代の預け入れ: 委任アドレスのガス代 0.111 ETH から 0.05 ETH をコントラクトへ(見学モード開始時)。

  → 上記ソースの castSnapshotVotes() / _castVote() を読む。

【主張3】対応表の誤登録に 24 時間の取消猶予がある(本番設定)
  → ソースの registerProposal() で eligibleAtBlock = block.number + registrationDelayBlocks、
    unregisterProposal() は snapshotVotesAccepted != 0 なら revert、
    setRegistrationDelayBlocks() が既登録の eligibleAtBlock に影響しないことを確認。
    (テストネットの現在値は eth_call registrationDelayBlocks() = 5(実験用)。本番は 7200)

【主張4】管理者にも票の偽造・改変・任意の Nouns 投票をする権限がない
  → ソースの onlyOwner 関数を列挙する。setExcluded / setMarginBlocks / setLiveMode /
    setRegistrar / setRegistrationDelayBlocks / setRefundEnabled / setRefundCapPerProposal /
    sweep(+ OpenZeppelin Ownable 標準の transferOwnership / renounceOwnership)のみで、
    票を作る・書き換える・execute の結果を指定する関数がないこと。
    (registerProposal / unregisterProposal は owner も呼べるが、猶予と取消不能条件は §3 のとおり)
