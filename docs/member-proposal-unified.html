Snapshot での投票はそのまま。その前後の手作業をなくします

3 行まとめ

  • その後の「結果を確認して Nouns DAO に投票する」定常的な人手作業(現状は年 20〜28 時間)を、署名をオンチェーンで検証して自動投票する仕組みに置き換えます。費用はガス代のみ 年 約 0.003〜0.006 ETH(1,100〜2,300 円)。当面のガス代はアールグレイが準備するため、新たなトレジャリー支出はありません(いまの委任アドレスにあるガス代はそのまま温存します)。

1.提案 1 本ごとの流れ

いまの仕組み

  1. 自動ローカル 自宅 PC が Nouns の新提案を検知し、AI で日本語要約を作る
  2. 人クラウド アールグレイが GitHub 上で要約を確認・修正して承認
  3. 自動クラウド GitHub 上の自動処理が Snapshot に投票ページを作成(本文＝日本語要約)
  4. 人クラウド Discord に「投票してください」と告知
  5. メンバークラウド Snapshot で投票(署名・ガス代 0 円)
  6. 人オンチェーン 締切を見張り、結果を確認し、自分のウォレットから Nouns DAO に投票
  7. 人クラウド Discord に結果を報告

新しい仕組み

  1. 自動クラウド Nouns の新提案の投票開始を自動検知(GitHub 上で 20 分ごとに巡回・自宅 PC 不要)
  2. 自動クラウド Snapshot に投票ページを作成(GitHub 上)。本文は Nouns の提案文をそのまま転記(長すぎる場合のみ末尾を省略し、原文リンクを表示)
  3. 自動オンチェーン 「この Snapshot 投票は Nouns の第 N 号議案のもの」という対応付けを記録
  4. 自動クラウド Discord に告知(投票リンク・締切つき)
  5. メンバークラウド Snapshot で投票 (画面も手順も変わりません・ガス代 0 円)
  6. 自動オンチェーン 投票の署名がコントラクトに届き、本物か検証され、NFT の枚数で集計される
  7. 自動オンチェーン 締切後、コントラクトが集計どおり Nouns DAO に投票
  8. 自動クラウド Discord に結果を報告(検証リンクつき)
変わること
  • 定常的な人の作業を自動化します(告知・Nouns への投票・結果報告)。障害時の確認や手動対応は残ります。集計から投票・報告までの通常の流れは自宅 PC に依存しません。
  • Snapshot の提案文が「日本語要約」から「Nouns の原文(英語)そのまま」に変わります。画像や見出しもそのまま表示されます。日本語の要約をどう扱うかは今後検討します。
変わらないこと: メンバーの投票体験。今までどおり Snapshot で、署名だけ・ガス代 0 円で投票します(ETH を持っていないウォレットでも投票できます)。

2.誰が何を持つか — 権限と鍵

いまの仕組み

  • Nouns の投票権 … マルチシグ → アールグレイ個人のウォレットに委任
  • 投票の判断 … 人が Snapshot の結果を読んで手で実行
  • Snapshot の結果と Nouns への投票の一致は、人が正しくやったと信じるしかない
  • アールグレイが不在・多忙だと止まる

新しい仕組み

  • Nouns の投票権 … マルチシグ → コントラクトに委任(個人は持たない)。つまり「アールグレイ(人)への委任」を「コントラクト(自動)への委任」に置き換える提案です
  • 投票の判断 … コントラクトが署名を検証して自動集計。運営もクラウドも受理済みの票や集計値を書き換えられない
  • 集計の内訳が Nouns DAO の記録に残る(§5)。誰でも検算できる
  • クラウドが止まっても投票は無効にならない。運営以外の第三者でも代わりに反映・実行できる(ウォレット操作などの技術的スキルは必要 — §6)

この仕組みを動かす 4 つの鍵 — 誰が何をでき、何をできないか

自動化にはチェーンや Snapshot へ送信するための鍵(ウォレット)が要ります。大事なのは1 本の万能な鍵を作らないことです。役割ごとに独立した鍵に分け、それぞれに「できること」を最小限だけ持たせます。この分担はテストネットとメインネットのリハーサルで実際に構成して動作確認済みです。

鍵が盗まれたら何が起きるか — 「いちばん漏れやすい場所に、いちばん弱い権限」

最も漏えいリスクが高いのは、ネットに常時つながっているクラウドです。そこで、クラウドに置くリレイヤーの鍵にはコントラクト上の特別な権限を持たせていません。仮にリレイヤーの鍵が盗まれた場合の主な被害は次のとおりです。

  • 自動投函を妨害・遅延させる(対策は §3 — 誰でも代わりに運べ、締切時の照合で検出されます)
  • リレイヤー用ウォレットの残高を盗む(本番想定は 0.01 ETH。返金プールやトレジャリーを直接引き出す権限はありません)

逆に、できないこと:

  • 票の偽造・改変・勝手な投票 — §3 のとおり、署名の数学的性質により成立しません。
  • ガス払い戻しでプールを吸い出すこと — 理由は 3 つあります。
    • 払い戻しは「本物の署名を実際に反映できた仕事」にしか出ません。同じ票の再提出は失敗し、失敗には 1 円も出ません。
    • 使った以上の額は戻りません(攻撃者の利益はゼロ)。さらに提案ごとの累計上限 0.02 ETH と、管理者の無効化スイッチで頭打ちです。
    • そもそも票をチェーンに送る操作(投函)は誰でも実行できる設計なので、鍵が漏れても「払い戻しを受けられる」能力は何も増えません。

つまりコントラクト上の票を偽造・改変する権限は増えませんが、自動処理の停止と、リレイヤー残高(本番想定 0.01 ETH)の損失は起こり得ます。対処は鍵の差し替えと残高の補充です。加えて本番では、4 つの役割に同一アドレスが混ざっていないかを導入時のチェックで照合し、Worker 自身も owner・登録係・リレイヤーの重複を検出すると停止します。

置き場所を分ける理由 — 特に bot と登録係

  • 投票を「運ぶ人」(Cloudflare)と「作る+登録する人」(GitHub)を分けます。Cloudflare が盗まれても対応表の登録はできず、GitHub が盗まれても票を運ぶ鍵は別にあります。bot と登録係を一体にしているのは、作成と登録を同じ処理にすると「どの Snapshot 提案がどの議案か」を探す曖昧さがなくなり、取り違えや乗っ取りの経路が減るためです。
  • 設計上の限界: 票の投函は誰でも実行できる操作(§6 の救済経路)なので、GitHub 側(bot と登録係)が両方乗っ取られると、偽の投票ページを作って対応表に登録し、メンバーが署名すれば誰でも投函できてしまいます(Cloudflare を破る必要はありません)。この「対応表への誤登録・偽登録」に対する最後の砦は、§3 のとおり管理者による停止 + その議案の手動投票です。Cloudflare のリレイヤー鍵だけが漏れた場合にできるのは投函の妨害・遅延だけで、票の偽造や勝手な登録はできません。ただし Cloudflare のアカウントや配信サーバーごと乗っ取られた場合は、投票ページ(状況ページ)を偽画面に差し替えてメンバーに意図と違う署名をさせる、といったフィッシングは起こり得ます(この場合も対応表の登録や票の偽造はできず、メンバーは Snapshot 公式画面から投票すれば影響を受けません)。
  • 管理者権限の移管(将来マルチシグへ移す場合)は 1 トランザクションで完了します。テストネットで移管の往復を演習済みです。

3.「集計が正しい」と言える理由

いちばん大事な前提: コントラクトは「集計結果」を受け取りません。受け取るのは1 票ずつの署名データで、正しさを自分で確かめ、集計も自分で行います。「誰かが計算した結果を信じる」場面がそもそも存在しません。

そもそもコントラクトは Snapshot を読めないのに、どう検証するのか

コントラクトは外部のインターネットに一切アクセスできません(あらゆるスマートコントラクト共通の制約)。Snapshot から署名データをダウンロードするのはリレイヤー(クラウドの自動プログラム)で、トランザクションの引数としてコントラクトに「手渡し」します。つまり運び屋です。

「運び屋が渡すデータなど信用できるのか?」 — ここが設計の核心で、信用しなくていいようにできています。メンバーが snapshot.box で「賛成」を押すと、ウォレットが「誰が・どの投票所の・どの提案に・どの選択肢を・いつ」という構造化されたメッセージ全体に電子署名を作ります(チェーンに書き込まないのでガス代 0 円)。この「メッセージ+署名」の組が Snapshot と IPFS に公開保存され、誰でもダウンロードできます。

電子署名には次の性質があります: 署名とメッセージがあれば、「誰が署名したか」を純粋な計算だけで復元できる(誰かに問い合わせる必要がない)。コントラクトは受け取ったデータから、①メッセージのハッシュ値を自分で計算し直し(このとき投票所名は、デプロイ時にコントラクトへ焼き込まれたスペース名を使う — 本番は pnounsdao.eth)、②署名から署名者のアドレスを数学的に復元し、③申告された投票者と一致するか照合します。Ethereum 本体が全トランザクションの検証に使っているのと同じ仕組み(署名アルゴリズム ECDSA が同一という意味)です。

リレイヤーが途中で「賛成」を「反対」に書き換えると、①のハッシュが変わり、②で復元されるアドレスがまったく別の(実在すらしない)アドレスになり、票は拒否されます。改ざんは「バレる」のではなく数学的に成立しないのです。偽の票をゼロから作るには本人の秘密鍵が必要で、それは本人のウォレットの外に出ません。

たとえるなら: Snapshot は「実印を押した投票はがきが貼り出される公開掲示板」、リレイヤーは「はがきを役所に運ぶだけの配達員」、コントラクトは「印影を自前で照合できる役所」です。役所は掲示板にも配達員にも「本物ですか?」と聞く必要がなく、はがきそのものを検査すれば真贋が分かります。配達員にできるのは配達をサボることだけで、それも掲示板が公開なので誰にでも露見します。

1 票が通る主要 8 項目の確認

#確認することどうやって確かめるか
1この投票はどの Nouns 議案のものか署名に含まれる Snapshot 提案 ID から、事前に登録された対応表(§2 の登録係が提案ごとに登録する「この Snapshot 投票 = 第 N 号議案」の一覧)を引く。未登録なら受け付けない
2対応表が登録された直後ではないか登録の直後(10 ブロック・約 2 分)は票を受け付けない(登録と受付開始が同じ瞬間にならないようにする最小間隔)
3署名が本物か受け取ったデータ(投票所名・議案 ID・選択肢・時刻・投票者など)からコントラクトが自分でハッシュを計算し直し、署名から投票者のアドレスを復元。申告と一致しなければ拒否
4Safe など複数人で承認するウォレットからの投票かこの種のウォレットは、ウォレット自体が Ethereum 上のプログラム(コントラクト)で、1 本の署名鍵を持たないため、確認 3 の計算が使えません。代わりに、投票者として名乗っているそのアドレス — つまり投票者自身の Safe コントラクト — に「この署名を有効と認めるか」をチェーン内で問い合わせます(EIP-1271 という共通規格)。この問い合わせに人が応答するわけではありません — Safe コントラクトに組み込まれたプログラムが「必要な人数の承認が署名データに含まれているか」をその場で機械的に検査し、自動で即答します(承認集め自体は投票のときに Safe のアプリ上で済んでいるもので、問い合わせの時点で誰かの操作を待つことはありません)。Snapshot などチェーン外への問い合わせでもありません
5本当に投票権があるか添えられた NFT 番号を1 枚ずつ pNouns NFT に照会し、現在の持ち主が署名者本人か確認
6同じ NFT を二重に数えていないか議案ごとに「この NFT は計上済み」を記録(他人に移して再投票しても数えられない)
7投票のやり直しの整合性同じ投票者の署名は、時刻がより新しいものだけ有効(古い署名の再提出は拒否)
8期限内かNouns 側の議案が投票可能な状態で、締切前であることを確認

表は主要な検査です。このほかに除外アドレス・選択肢の値・データ形式などの検査があり、署名の確認は通常ウォレット(ECDSA)とスマートウォレット(EIP-1271)で経路が分かれます。Nouns 側の投票期間の確認はその議案の最初の票を受理するときに行われ、集計の締切はその時点で固定されます。

なぜ運営にもクラウドにも書き換えられないのか

  • 署名は 1 文字でも変えると別人の署名になります。「賛成」を「反対」に書き換えて送っても、確認 3 で復元されるアドレスが変わり、本人と一致せず弾かれます。
  • 票の重みは水増しできません。署名には「何枚持っているか」は入っていません。運ぶ側が NFT 番号を添えますが、コントラクトが 1 枚ずつ実際の持ち主を照会するため、他人の NFT や架空の保有は通りません。
  • 別の投票所の署名は使えません。対象の Snapshot スペース名がコントラクトに焼き込まれており、ハッシュ計算に使われます。攻撃者が自分で作った投票所の署名を持ち込んでも成立しません。

使っている暗号は堅牢か

この仕組みが通常ウォレットの検証で使う暗号部品は Keccak-256(ハッシュ)とECDSA/secp256k1(署名)の 2 つで(スマートウォレットの署名はそのウォレットが実装する標準判定 = EIP-1271 に従います)、どちらも Ethereum 本体が全取引の検証に使っているものと同一です(自作の暗号は一切ありません)。Keccak-256 は世界公募(SHA-3 コンペ)の優勝作で、15 年以上の解析を経ても実用的な攻撃は 1 件も見つかっていません。

もしこれらが破られる日が来たら、pNouns の投票どころか Ethereum 上の全資産(Nouns の NFT もトレジャリーも)が同時に危険になります。つまりこの仕組みの暗号的な安全性は「Ethereum 自体と同じ水準」で、ここが相対的な弱点になることはありません。ハッシュの取り方も生の連結ではなく EIP-712 という標準規格で、型情報や用途(snapshot)ごと封印するため、別の文脈で作った署名を投票に流用するすり替えも成立しません。(参考: かつて広く使われた MD5 のように、ハッシュ関数が後年破られた例は実在します。Keccak-256 は出力長も設計世代も異なり、現時点でその兆候はありません)

補足: 遠い将来の量子コンピュータはハッシュより署名側への脅威が先に来るとされますが、これは Ethereum 全体の課題で移行方式が研究されており、この仕組み固有のリスクではありません。実務上の最弱点はアルゴリズムではなく鍵の管理と対応表の運用です — だからこそ鍵の分離(§2)や対応表の自動検算(§3)に力を入れています。

運ぶ側(クラウド)にできてしまうことと、その対策

リレイヤー(運び屋)が悪意を持った場合にできることは、具体的には次の 2 つだけです。

  • 都合の悪い票だけ届けない・遅らせる — 例えば「賛成票だけ運ばず、反対票だけ届ける」ように、届ける票を選り好みして集計を歪めようとする。
  • 票の重みを実際より小さく届ける — 票をチェーンに送るとき、リレイヤーは投票者が持つ NFT の番号一覧を添えます(署名には「何枚持っているか」が入っていないため)。ここで 5 枚持っている人の票に 1 枚分しか添えなければ、その人の票の重みが 5 → 1 に減ります。

どちらにも対策があります。

  • 届けない → 署名は Snapshot 上で公開されているので、誰でも同じ署名を拾って代わりに届けられます(リレイヤーに独占権はありません)。
  • 重みを削る → 誰でも同じ署名に残りの NFT 番号を添えて出し直せます。コントラクトはまだ数えていない NFT の分だけを追加で計上します(同じ人を二重に数えることはありません)。
  • それでも漏れたら → 確定の直前に「Snapshot 上の投票者数」と「チェーン上に反映済みの投票者数」を突き合わせ、足りないままなら本番では自動確定しません(警告を出して人の判断を仰ぎます)。運び漏れが最終結果になることを防ぐ最後の砦です。

唯一、暗号で保証できない部分 — 対応表

確認 1 の対応表(この Snapshot 投票 ＝ Nouns の第 N 号議案)だけは、コントラクトが自力で確かめられません。Snapshot の投票署名に Nouns の議案番号が含まれていないためです(Snapshot の仕様)。運用は全自動ですが、「そのプログラムと鍵を信頼している」という意味で、ここだけは性質が異なります。

そのための備えを 4 段用意しています。

  1. 登録の直後(約 2 分)は票を受け付けない — 登録と受付開始を同じ瞬間にしないための最小間隔です。
  2. プログラムが自分で対応付けを検算する — Snapshot に作る提案には、元の Nouns 提案ページの URL(nouns.wtf/vote/第N号)を議論リンク欄(discussion)に必ず設定します。プログラムは処理のたび(本番は 2 分ごと)に対応表の「この Snapshot 提案 = 第 N 号」を取り出し、その Snapshot 提案の議論リンクが本当に第 N 号の URL を指しているかを照合します。食い違っていれば Discord に⚠️警告を出し、本番ではその議案の処理(告知・反映・確定)を止めます。
  3. 対応表はオンチェーンに公開され、Discord の告知にも両方の ID が出るので、誰でも見比べられます。
  4. 最終手段として管理者(アールグレイの管理用ウォレット。将来移管すればマルチシグ)が停止できます。

備え 1(約 2 分の受付停止)と備え 2(自動検算)の詳しい理屈と限界

備え 1「約 2 分の間隔」の役割と限界:
役割 — 対応表は、票を 1 票でも受け付けた後は取り消せない仕様です(受理済みの票を無効化させないため)。そこで登録から約 2 分は票を受け付けず、その間に自動検算(備え 2)が必ず 1 回は走って、誤登録なら⚠️警告が出るようにしています。この間隔が無いと、取り違え事故が起きたとき、誰も気づく前に自動のリレイヤー自身が普段どおり票を投函して、誤った対応表を取消不能にしてしまいます。2 分あれば「票が入る前に警告 → 取り消して正しく登録し直す」という軽い復旧で済みます。
限界 — 投函は誰でもできる操作なので、受付開始の直後に悪意の第三者が票を投函すれば、対応表はその時点で取消不能になります。つまりこの 2 分は「取消の機会」までは保証せず、「検算が受付より先に走ること」を保証する仕組みです。
それでも安全な理由 — 対応表が取消不能になっても、確定(Nouns DAO への投票)までには集計締切まで数日あります。検算の⚠️警告(数分で出ます)を受けて管理者が停止すれば、誤った投票が Nouns に届くことはなく、その議案は従来どおり手動で投票します(停止は Nouns への最終投票だけを止め、集計は続きます)。
補足 — 受付開始の時点は登録の瞬間に固定され、管理者にも前倒しできません(万一管理者の鍵が漏れても、検算の機会を奪えないようにするためです)。なお巡回間隔が「2 分」なのは釣り合いの値です: 投票からオンチェーン計上までの時間差(この間に NFT を移転すると票が減り得る窓・§4)をできるだけ短くしたい一方で、登録猶予(約 2 分)の間に自動照合が必ず 1 周まわること、無料枠のクラウド利用の範囲に収まることを両立させています。

備え 2「自動検算」がなぜ誤登録に気づけるのか: 対応関係は 2 箇所に書かれています — ①オンチェーンの対応表(「この Snapshot 提案 ＝ 第 N 号」)と、②Snapshot 提案自身の議論リンク欄(作成時に nouns.wtf/vote/第N号 を必ず埋め込む)。正しく作られていれば両者は同じ番号を指すので、プログラムは 2 分ごとに①と②の番号を突き合わせ、食い違えば⚠️警告を出して本番ではその議案の処理を止めます。
具体例: 第 990 号のミラー(議論リンク=/vote/990)を誤って「第 991 号」として登録すると、対応表は 991・リンクは 990 で必ず食い違い、登録から 2 分以内(受付開始前)に警告が出ます。
警告は消せません: 検算は 2 分ごとに走り続けるため、第三者が票を投函して対応表を取消不能にしても、警告と処理停止はそのまま続きます。投函で得られるのは「登録の削除を封じる」ことだけで、誤った投票を Nouns へ届けさせる力はありません。
限界: リンクは提案を作った人の自己申告なので、捕まえられるのは取り違え事故や雑な攻撃までです。bot と登録係の両方の鍵を同時に握った攻撃者が、リンクまで正しい偽提案を作って登録した場合、機械の警告は出ません。そこは備え 3・4 の担当です。

脅威誰が・どう止めるか
取り違え事故・雑な攻撃(番号が食い違う)機械が数分で⚠️警告 → 票が入る前なら取消して登録し直し。入った後も処理停止のまま人が対応
精巧な攻撃(bot と登録係の両鍵を同時に奪い、リンクまで正しい偽提案を登録)自動警告は出ない。ただし偽提案・登録・告知はすべて公開の場で起きるため人の目に触れ(備え 3)、発覚から Nouns への確定までの数日の間に管理者が停止すれば誤投票は 1 件も届かない(備え 4)。当該議案は手動投票へ

検討事項(未実装): 正規の提案はすべて bot が作るため、「対応表に載った提案の作成者が正規の bot か」を検算に加えることもできます。追加すれば「登録係の鍵だけが漏れた」ケースも自動警告になります(両鍵同時漏えいには効きません)。導入時までに実装するかを検討します。

投票したのに反映されない可能性はあるか(全ケースの一覧)

先にまとめ: 気をつけることは 1 つだけ — 「投票した直後に、その pNouns を誰かに送る」ことをしない。票は通常、投票の数分後に自動でオンチェーンに反映されます。目安として投票後 10 分ほど NFT をそのままにし、確実を期す場合は状況ページで反映を確認してから動かしてください(ウォレット接続不要で誰でも閲覧できます。§10 にも記載)。反映が済んだあとは、NFT を動かしても集計は一切変わりません。普通に投票して普通に持っているだけなら、何も心配はいりません。

そのうえで、メンバーの操作や運用に由来して票が計上されない・減る可能性は次の 3 つです。このほかシステム側の異常(署名データの取得不能・通信障害など)で反映が遅れる・止まることがありますが、いずれの場合も本番では未反映のまま勝手に確定せず、人の確認に切り替わります(§6)。

ケース何が起きるか備考
① 投票のあと、反映される前に NFT を移転した手放した分は数えられません(残した枚数だけ計上)。全部手放すと、その票は自動反映の対象から外れます(Snapshot の画面では投票済みに見えるままです)。締切時に未反映の票が残っていれば、本番では自動確定を止めて人が確認します(§6)本人の操作が原因。注意: 譲り受けた人がスナップショット時点で pNouns を保有していなければ、この議案では投票できず、その NFT 分の票は使われないままになります。保有していて投票資格がある場合は、譲り受けた NFT も含めてその人の票として計上され得ます。次の議案からは、どちらの場合も新しい持ち主が普通に投票できます
② 集計締切までに票が運ばれなかった(クラウドの長時間障害)締切後の追加はできません。ただし未反映の票が残ったまま本番が勝手に確定することはなく、自動確定を止めて人の判断に切り替えます(§6)障害が原因。署名は公開されているので、締切前なら誰でも代わりに運べます
③ 除外アドレス(トレジャリー 13 枚)からの投票ルールどおり数えません(§9)設計どおり

反映された後の移転は、集計に影響しません。あなたの票はそのまま有効で、取り消されることはありません(Snapshot 自体の「投票時点の権利で確定する」挙動と同じです)。譲り受けた人は、同じ議案ではその NFT で投票できませんが(計上済みのため)、次の議案からは普通に投票できます。どの場合も同じ NFT が 1 つの議案で 2 回数えられることはなく、移転で票を増やすことはできません。

ひとことで言うと: 「Snapshot の使い勝手(署名だけ・ガス 0 円)を残したまま、各署名と集計を第三者が検算できる形でオンチェーンに引き上げ、Nouns DAO への反映まで自動化した」仕組みです。投票の入り口である Snapshot と、議案どうしの対応表には依存が残ります。

5.オンチェーンに残る記録 — Nouns DAO と pNouns Voter

6.クラウド(Cloudflare)が止まったらどうなるか

票そのものは Snapshot に残るため、Cloudflare の停止だけで署名が消えるわけではありません。集計の締切は Nouns の投票終了より 7,200 ブロック(約 24 時間)早く設定し、その後の Nouns DAO への確定操作に余裕を持たせます。ただし、Snapshot の票をコントラクトへ反映できるのはこの集計締切までです。締切後に未反映票が見つかった場合、自動確定は停止しますが、その票を遅れて追加することはできません。

運営者に何かあったら — 仕組みの再構築可能性

自動処理はアールグレイのアカウント(Cloudflare・GitHub)で動いていますが、アカウントが停止しても仕組みは失われません。

  • 止まらないもの: コントラクト・全記録(オンチェーン)、メンバーの票(Snapshot/IPFS 上に公開)。誰のアカウントにも依存しません。
  • すぐできること: 進行中の議案は、公開署名を使った代理投函・手動 execute で完走できます(この節の救済経路)。
  • 再構築: リレイヤーはコントラクト上の特権がないため、誰でも新しい鍵と自分のアカウントで立て直せます。Snapshot bot はスペース管理者が交代させられます。登録係は管理者(owner)が交代操作で差し替えます。自動処理のソースコードはGitHub で公開済みなので、「リポジトリを自分のアカウントに配備し直す」だけの作業です(手順書も同リポジトリにあります)。
  • 唯一の急所は管理者の鍵です。失われると当該コントラクトでの新規登録・停止・資金回収ができなくなりますが、その場合も最終手段として「新しいコントラクトを公開ソースからデプロイし直し、マルチシグが委任先を変える」ことで復旧できます。将来マルチシグへ移管すれば(§9)、この急所自体が個人から DAO に移ります。

Cloudflare の中身は検証できるのか(できること・できないこと)

直接は検証できません。Cloudflare 上で実際に動いているプログラムが、公開しているソースコードと同一であることを第三者が証明する方法はありません(これは世の中のあらゆるサーバーに共通の限界です)。だからこそ、この設計はクラウドを信頼しないことを前提にしています: クラウドは署名の投函、誰でも呼べる確定操作、通知を自動実行しますが、票の中身はオンチェーンのコントラクト(こちらはソースコードとの一致を誰でも検証可能)が確かめます。クラウドの動きも外から観測はできます — 送信したトランザクションは全部チェーン上に残り、設定は公開 API(§10)で見えます。「中身は見えないが、票の偽造・改変はコントラクトが拒否し、運び漏れは公開データとの照合で検出する」という位置づけです。

9.投票のルール / 導入の進め方

投票のルール(コントラクトに固定)

  • 重み = 保有 pNouns 枚数(チェーン上で検証)。トレジャリー分(13 枚)は数えない(DAO 自身の持ち分で特定メンバーの意思を表さないため — 現行 Snapshot 運用の踏襲)。技術的には除外リストにトレジャリーのアドレスを登録する方式で、将来ルールを変える場合も管理者が除外設定を変更するだけで、コントラクトの書き換えは不要です。定足数なし。
  • 同数なら投票者数が多い方、それも同数なら棄権 (暫定 — ご意見で変更可能)。誰も投票しなければ Nouns にも投票しない。
  • Snapshot で投票をやり直した場合は、いちばん新しい投票が有効。
  • 集計の締切は Nouns の投票終了の 7,200 ブロック前(約 24 時間前)。メンバーの投票期間は今までどおり Snapshot の 48 時間で、締切はその後の反映・確定のための余裕です(§1 のスケジュール参照)。
  • コントラクトは後から書き換え不可。NFT や資産は預けません(預けるのはガス代のみ)。

導入の進め方

「機械チェック」とは: 各段階の間で、設定値・鍵の分離・委任の状態・各所の残高が想定どおりかを、照合プログラムがオンチェーンの実際の値と突き合わせて全項目確認することです。人の目視や思い込みではなく、全項目 ✅ にならない限り次の段階へ進みません(照合プログラムはテストネットとメインネットのリハーサルで使用済みです)。

  1. 先行リハーサル(実施中・メンバー合意の前・アールグレイ費用負担) — メンバーに提案する前に、メインネット上にテスト用の Snapshot スペース向けで設置し、実在の Nouns 提案・実際のガス代・実際の時間の流れで通しを検証します(§8 参照)。テスト用コントラクトも見学モード(本番スイッチ OFF)で運転します。仕上げに、委任前の「投票トランザクション」テストのときだけ一時的にスイッチを入れます: 委任がなく投票の重みが 0 のため実際の賛否に一切影響しない状態で、コントラクトが Nouns DAO へ本当に投票を送信できることまで確認します。pNouns の現行運用・Snapshot・Discord には一切影響しません。ここで問題が出れば直してから、次の段階に進みます。
  2. 本番用コントラクトを見学モードで設置(メンバーへの紹介・周知の後。pNouns 用スペース pnounsdao.eth 指定で新たに設置) — 本番スイッチは OFF のまま、Nouns には投票せず、集計だけを実際の提案で数回行い、手動運用の結果と一致するか確認します。仕上げに、①と同じ委任前の「投票トランザクション」テストをこの本番用コントラクトでも 1 回行います(一時的にスイッチを入れ、重み 0 の無害な投票で castVote までの全経路をこのデプロイで実証してから、スイッチを OFF に戻して委任を待ちます)。この間も現行の手動運用は継続するため、メンバーの投票の流れと Nouns への反映は今までどおりです(裏で自動集計が並走し、一致を Discord で報告します)。この段階でアールグレイが準備した ETH から、返金プールへ 0.05 ETH、リレイヤーへ 0.01 ETH、登録係へ 0.005 ETH を配分します(委任アドレスの既存ガス代は温存)。コントラクト管理者は設置の時点からアールグレイの管理用ウォレット(vote.earl-grey.eth)です(操作のガスはアールグレイ負担・預かり金は使いません)。
  3. 一致の確認 → メンバーの合意 — 見学モードの自動集計と手動運用の結果が複数の提案で一致したことを確認し、その実績と本資料を添えてメンバーに諮ります。合意の方法は、いつもの pnounsdao.eth での Snapshot 投票を想定しています(議題:「Nouns 投票権の委任先を、アールグレイ個人のウォレットからこのコントラクトへ変更する」ことへの賛否)。
  4. マルチシグが投票権の委任先をコントラクトへ変更(1 トランザクション・いつでも戻せる)→ 委任が効いたことを機械チェックで照合 → 管理者が本番スイッチ(setLiveMode(true))を入れて本番開始。「投票を送るかどうか」はスイッチが、「票の重み」は委任が、それぞれ独立に決めます。②の仕上げのテストは「スイッチ ON × 委任なし = 重み 0 の投票」、この段階は「スイッチ ON × 委任あり = 本番」です。委任だけしてもスイッチが OFF なら投票は始まらないため、委任が効いたこと(コントラクトの Nouns 投票力が、委任した Nouns の枚数と一致したこと)を冒頭の機械チェックで照合してからスイッチを入れる、という順序にしています(委任の変更は「以後の提案から」しか効かない遅いスイッチ、liveMode は数分で効く速いスイッチ、という役割分担でもあります)。
  5. 当面の管理はアールグレイ(委任アドレス)が担当します。安定稼働を確認した後、pNouns マルチシグへの管理者権限の移管を検討します(1 トランザクション。移管手順はテストネットで演習済み。移管後は緊急停止・ガス回収・鍵交代にマルチシグの承認が必要になります)。
